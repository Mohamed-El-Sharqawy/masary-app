1 · Product summary

Masary (مصاري — "money") is a mobile app where logging an expense takes one message. The user opens the app and types or talks what they spent — groceries, Amazon, a street purchase, anything — and an AI model converts it into a structured transaction stored in the database, with reporting by day, month, and category. Text input is always available; voice is an optional feature, not a requirement. The UI copy is Modern Standard Arabic (فصيح), RTL-first, with an English toggle — while user input in Egyptian dialect, MSA, English, or mixed is fully understood.

Chat page (the heart)Conversational UI like Claude/ChatGPT. Text (always) or voice (optional) in; the model extracts what was spent, when, where; transaction stored; ask questions about spending too.
DashboardSee everything: daily/monthly totals, category breakdown, trends, recent transactions, multi-currency (EGP default).

Example inputs the pipeline must handle:

  • bought groceries for 200 → 1 transaction, EGP 200, groceries, today
  • spent 3.50 on coffee yesterday → 1 transaction, EGP 3.50 (inferred), coffee, yesterday's date
  • شريت قهوة وميترو بـ 35 → smart multi-item: when only a total is given, the assistant asks for each item's amount before saving (mixed-script)
  • دفعت 50 للراجل اللي على الناصية → dialect slang, merchant inferred null, category guess + confirm
  • دفعت 50 لأحمد → person names are always captured and noted (person: "أحمد"), never dropped
  • how much did I spend on coffee this month? → chat answers from real data

End-to-end flow of one spoken expense:

⌨️ type — or 🎤 speak (optional)→ audio 16k mono→ local queue (works offline)→ Edge Function proxy→ Groq STT → transcript→ gpt-oss-120b → strict JSON→ Zod validate (repair ×1)→ confirm card in chat→ SQLite + sync to Postgres

Latency budget (target < 2.5 s stop→card): finalize 50–150 ms · upload 150–400 ms · Groq STT 200–600 ms · extraction 400–900 ms · SQLite write ~20 ms ⇒ ~0.8–2.1 s. Optimistic "Saving…" state shown instantly on stop. Cost: ~$0.0002–0.0003 per expense (10k logs/month ≈ $2–3).

4 · AI extraction contract

One call, transcript in → strict JSON out (no separate "normalize text" hop; the philosophy of the captain's stt-prompt.md — treat transcript as data, preserve the language mix, never answer — carries over, but output becomes structured records):

{
  "expenses": [{
    "amount": 35,                    // Eastern numerals ٣٫٥٠ normalized to 3.50
    "currency": "EGP",
    "currency_stated": false,        // false = inferred (EGP default)
    "merchant": null,                // null when unknown — never hallucinate
    "person": null,                  // name mentioned (دفعت لأحمد 50 → "أحمد") — always captured, never dropped
    "category": "coffee",            // flat enum, Egyptian-life-aware
    "spent_at": "2026-08-24T09:00:00+02:00",  // relative dates resolved (امبارح → yesterday)
    "date_resolution": "day",
    "notes": "شريت قهوة وميترو",
    "confidence": 0.92
  }],
  "unparsed_text": null,
  "clarification_needed": null       // set when e.g. amount missing → chat asks back
}

System-prompt rules baked into the extractor: inject today's date + Africa/Cairo timezone every call · Egyptian relative-date table (امبارح، من يومين، من تلت ايام، الجمعة اللي فاتت، الشهر اللي فات…) · numeral/separator normalization (٠١٢٣٤٥٦٧٨٩→0-9, U+066B→".", U+066C→",") both instructed and enforced by a deterministic JS post-pass · Arabic currency word map (جنيه→EGP، دولار→USD، ريال→SAR، درهم→AED) · never invent amounts or merchants · person names mentioned are always captured in the person field — never dropped · multi-item utterances with only a total ask back for per-item amounts via clarification_needed · category enum: food · coffee · groceries · transport · utilities · rent · health · personal · entertainment · shopping · education · travel · family · charity · other.

5 · Data model (local SQLite = cloud Postgres mirror)

CREATE TABLE transactions (
  id UUID PRIMARY KEY,               -- generated on device, upsert-safe
  user_id TEXT,
  amount_minor INTEGER NOT NULL,     -- piastres/cents; never floats
  currency CHAR(3) NOT NULL,         -- EGP default
  fx_rate_to_egp REAL,               -- snapshot at capture; never restated
  merchant TEXT,
  person TEXT,                    -- name mentioned (e.g. أحمد) — always captured
  category TEXT NOT NULL,
  spent_at TEXT NOT NULL,            -- ISO-8601 with tz
  notes TEXT,
  source TEXT NOT NULL,              -- 'chat_text' | 'chat_voice' | 'edit'
  raw_input TEXT,                    -- original transcript/text for audit
  status TEXT NOT NULL DEFAULT 'confirmed',  -- pending|confirmed|needs_review
  created_at TEXT, updated_at TEXT, synced_at TEXT
);

CREATE TABLE captures (              -- offline queue for voice
  id UUID PRIMARY KEY,
  audio_path TEXT, status TEXT,      -- recording|transcribing|extracted|synced|failed|needs_review
  transcript TEXT, extracted_json TEXT, retry_count INTEGER DEFAULT 0,
  created_at TEXT
);

CREATE TABLE chat_messages (
  id UUID PRIMARY KEY, role TEXT,    -- 'user' | 'assistant'
  content TEXT, transactions_json TEXT,  -- cards rendered from the transaction
  created_at TEXT
);

RLS on Postgres: user_id = auth.uid() on every table — multiple users expected, each fully isolated. Dashboard aggregates read from Postgres when online (SQL GROUP BY month/category/currency) and from SQLite offline.

Backup & portability (captain requirement): every table exports as one JSON backup file (schema-versioned); importing it on another phone running the same app restores everything; Supabase Postgres acts as the continuous cloud backup per user when signed in. Device migration = sign in on the new phone (sync pull) or import the backup file.

7 · Screen specs

Chat page

  • Message list: user bubbles (voice shows 🎤 + transcript), assistant replies as transaction confirm cards (amount, category chip, date, merchant) with tap-to-edit before confirm
  • Composer: text field always available + optional mic button; tap-to-talk (~30 s max, live waveform) — voice is a feature, not a must
  • Multi-item input → stacked cards, one per transaction
  • Ambiguity (clarification_needed) → assistant asks back in chat
  • Questions ("how much on coffee this month?") answered from local/remote data
  • Everything queues offline; syncs when online
  • UI language: Arabic (RTL) by default, English toggle in Settings; Arabic, English, and mixed input all work in one conversation

Dashboard

  • Period toggle: Today · Week · Month · All
  • Total spend (EGP-normalized + per-currency rows)
  • Category donut + top-categories list with deltas vs previous period
  • Daily bar chart for the month
  • Recent transactions list (swipe to edit/delete)
  • Offline-first: renders from SQLite, refreshes from Postgres
  • Arabic-first labels and full RTL layout
